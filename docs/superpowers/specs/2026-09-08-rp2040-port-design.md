# K1 Firmware RP2040 Port — Design

**Date:** 2026-09-08
**Status:** Approved (replaces the ESP32-S3 target entirely)

## Decision

K1 firmware moves from the Seeed XIAO ESP32-S3 (ESP-IDF 5.x + `esp_tinyusb`)
to the **RP2040-Zero** (Waveshare design; hiBCTR clones on hand), built with
the **Raspberry Pi Pico SDK** and its bundled TinyUSB. The RP2040 replaces the
ESP32-S3 — there is no dual-target support. K1 never needed WiFi/BLE, the
RP2040 is cheaper, and its native USB + TinyUSB support is first-class.

## What does not change

- **Wire protocol** (`main/protocol.h`): 8-byte vendor HID reports, usage page
  `0xFF60`, VID `0x1209` / PID `0x0001` (dev), `KEY_EVENT` / `INFO` /
  `GET_INFO` messages, sequence byte semantics. Byte-for-byte identical.
- **Mac app (Magic Keys)**: zero changes. It matches on VID/PID/usage page and
  parses the same reports.
- **Debounce** (`main/debounce.c/h`): pure logic, 5 samples @ 1 kHz = 5 ms.
  Carries over untouched, along with its host unit test
  (`tests/host/test_debounce.c`).
- **Smoke test** (`tools/smoke_test.py`): host-side `hidapi` script; VID/PID
  and protocol unchanged, so it runs as-is.
- **Firmware-stays-dumb rule**: only debounced down/up events with a sequence
  byte; all gesture logic remains in the app.

## What changes

### Architecture: FreeRTOS tasks → bare-metal superloop

ESP-IDF forced FreeRTOS (scan task + report task + queue). The Pico SDK is
bare-metal by default and TinyUSB's idiomatic use is a main loop calling
`tud_task()`. The port drops FreeRTOS:

- `main()` loop: `tud_task()` → `k1_keys_poll()` → `k1_usb_flush()`.
- **Key scanning**: `k1_keys_poll()` self-paces to 1 kHz using
  `time_us_64()`; on each 1 ms tick it samples the three GPIOs, runs the
  debouncer, and pushes state changes into a `pico/util/queue` (32 entries,
  drop-oldest-behavior preserved: on a full queue the new event is dropped and
  logged, same as the ESP build).
- **Reporting**: `k1_usb_flush()` mirrors the old report task — answer a
  pending `GET_INFO` first, then drain one key event per call when
  `tud_hid_ready()`. Seq still only advances on successful `tud_hid_report()`.

The loop iterates in microseconds, so 1 kHz sampling jitter is negligible
versus the 5-sample debounce window.

### Files

| File | Change |

| `CMakeLists.txt` | Pico SDK project (`pico_sdk_import.cmake`, `PICO_BOARD=waveshare_rp2040_zero`) |
| `pico_sdk_import.cmake` | New — standard SDK import shim |

| `main/keys.c/h` | ESP GPIO/task/queue → Pico GPIO + polled scan + `pico/util/queue` |
| `main/usb_hid.c/h` | Descriptors/callbacks unchanged; `esp_tinyusb` install → `tusb_init()`; report task → `k1_usb_flush()` |
| `main/tusb_config.h` | New — TinyUSB device config (previously hidden in `esp_tinyusb` + sdkconfig) |
| `sdkconfig*`, `dependencies.lock`, `main/idf_component.yml` | Deleted (ESP-IDF artifacts) |

### Pins (RP2040-Zero)

Keys on **GPIO 0 / 1 / 2** (matching the CircuitPython bring-up script),
active-low to GND, internal pull-ups — same wiring style as before. Defined in
one array in `keys.c`. Debug logging via `printf` on UART1 (GPIO 8/9, 115200),
optional to wire — keys occupy UART0's default GPIO 0/1.

### Build & flash

- Toolchain: CMake + Ninja + `arm-none-eabi-gcc` + Pico SDK (pinned 2.x with
  TinyUSB submodule).
- `cmake -B build && ninja -C build` → `k1_firmware.uf2`.
- Flash: hold BOOT, plug in, drag the UF2 onto the `RPI-RP2` volume (or
  `picotool load`). No serial flasher, no `idf.py`.

## Error handling

Same posture as the ESP build: best-effort delivery. Queue overflow drops the
newest event with a log line; reports only send when the host is polling; a
failed `tud_hid_report()` does not advance the sequence byte, so the app's gap
detection only fires on real USB loss.

## Testing

1. Host unit test for debounce (unchanged, run in CI fashion locally).
2. Build must produce a UF2.
3. Hardware-in-loop: flash an RP2040-Zero, run `tools/smoke_test.py`
   (enumeration, GET_INFO round-trip, key events with jumper wire).

## Out of scope

- Enclosure CAD update — v2 CAD models the XIAO footprint; the RP2040-Zero is
  ~18×23.5 mm with a different pad layout, so the board pocket needs rework in
  a separate CAD task.
- The WS2812 RGB LED on the RP2040-Zero (GPIO 16) — LEDs remain out of scope
  for v1.
- OTA/DFU beyond the built-in BOOTSEL UF2 bootloader.
